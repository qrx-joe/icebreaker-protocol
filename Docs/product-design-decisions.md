# 破冰协议 · 产品设计决策文档

> 版本：v2.1.0 | 日期：2026-05-14 | 状态：待实现

本文档记录了基于本次产品审视会话所确定的所有设计决策，作为后续开发的执行依据。

---

## 一、品牌与命名

### 1.1 项目名称：保持 `icebreaker-protocol`（破冰协议）

**决策：不改名。**

理由：
- **隐喻精准**：完美主义者的状态就是"被冰封住了"（脑子在转，手被冻住）。"破冰"直击核心痛点。
- **Protocol（协议）的压迫感**：带有机器般的强制执行感，切断用户与系统"讨价还价"的退路。
- **辨识度极高**：赛博朋克 + 临床心理干预的独特调性，在同类工具中无可替代。

### 1.2 AI 助手命名：废弃"AI 助手"，改用 `[破冰协议]`

**决策：去人格化，使用 `[破冰协议]` 或 `[Protocol]` 作为对话框名称。**

理由：
- 用户无法对"协议"卖惨，无法对"系统"讨价还价。
- 彻底切断完美主义者"寻求情绪抚慰"的退路。
- 每一条回复都在强化"这是一套不可违抗的强制执行程序"的心智模型。

**备选方案（按威慑力排序）：**

| 名称 | 威慑力 | 说明 |
|------|--------|------|
| `[Protocol]` / `[破冰协议]` | ★★★★★ | 最推荐。去人格化，无法被说服。 |
| `协议督导` | ★★★★☆ | 有压迫感，但"督导"易触发被评判焦虑。 |
| `执行引擎` | ★★★☆☆ | 极客感强，但对话场景略显生硬。 |
| `领航员` / `破冰者` | ★☆☆☆☆ | 过于温和，不适合破冰场景。 |

## 二、UI 交互设计

### 2.1 AI 面板：废弃居中弹窗，改用右侧抽屉（Side Drawer）

**决策：`[破冰协议]` 面板以无遮罩右侧抽屉形式滑出。**

理由：
- 居中弹窗 + 黑色遮罩会挡住用户正在操作的"案发现场"。
- 用户向协议提问时，必须能同时看到左侧的步骤指令和输入框。
- 右侧抽屉符合"Copilot 伴随式"交互范式（参考 Cursor、GitHub Copilot）。

### 2.2 "需要帮助"按钮：从左下角移除，改为双触发机制

**决策：被动按钮 + 主动拦截并存。**

**机制 A：情境按钮（被动触发）**
- 位置：主输入框右下角内部（悬浮药丸按钮）。
- 文案：`⚡ 协议介入` （不要用"需要帮助"）。
- 逻辑：用户视线焦虑终点在输入框中央，按钮必须在触手可及之处。

**机制 B：停滞自动拦截（主动触发）**
- 触发条件：用户在当前步骤停留 ≥ 60 秒，且输入框字数无变化。
- 行为：`[破冰协议]` 面板自动从右侧弹出。
- 首句话：*"检测到你在这一步停留过久，[破冰协议] 已接管当前会话。不要思考，直接从下面 3 个灵感里选一个，或者告诉我你卡在哪了。"*
- 理由：完美主义者不会主动求助（羞耻感），系统必须主动介入。

### 2.3 提交按钮文案：废弃"问"，改用执行感文案

**决策：使用 `执行` 配合动态状态。**

| 状态 | 视觉表现 | 文案 |
|------|---------|------|
| 空状态（未输入） | 深灰色，不可点击 | `等待` |
| 就绪状态（已输入） | 高亮蓝色，可点击 | `执行 →` |

- 键盘映射：`Enter` 键 = 执行。
- 输入框下方微小提示：`Press Enter to Run Protocol`。

## 三、时长与节奏

### 3.1 每步时长上限：从 30 分钟压缩至 15 分钟

**决策：修改 `Step` 模型约束，`le=30` → `le=15`。**

```python
# server.py
class Step(BaseModel):
    title: str
    instruction: str
    output: str
    minutes: int = Field(ge=1, le=15)  # 上限从30改为15
```

理由：
- 时长决定任务在用户心中的"分量"。30 分钟会触发"这是大工程"的完美主义启动恐惧。
- **任务复杂性 → 增加步骤数量，而非增加单步时长。** 这是核心原则。
- 15 分钟是"心理安全红线"：足够产出雏形，又短到不给大脑"磨蹭"的机会。

**内置规则调整（`build_rule_steps`）：**

| 步骤 | 原时长 | 新时长 |
|------|--------|--------|
| 扩成初稿 | 20min | 12min |
| 写三个标题 | 10min | 5min |
| 改一句简历 | 15min | 8min |
| 完成投递动作 | 10min | 8min |

**AI 拆解 Prompt 新增约束：**
> "禁止生成预计耗时超过 15 分钟的步骤。如果任务复杂，必须将其拆解为多个 10 分钟以内的原子步骤。"

### 3.2 两阶段倒计时（Dual-Phase Timer）

**决策：前 30% 为乱写期，后 70% 为修整期，最后 60 秒为紧急状态。**

| 阶段 | 时间占比 | 颜色 | 协议提示 |
|------|---------|------|---------|
| 乱写期 | 前 30% | 绿色 | *"不准思考，把脑子里的垃圾先倒出来。"* |
| 修整期 | 后 70% | 蓝色 | *"修整到'别人能看懂'的程度即可。"* |
| 紧急状态 | 最后 60 秒 | 红色+抖动 | *"时间即将耗尽。立即交付！"* |

## 四、验收系统（三层验收闭环）

> ⚠️ **v2.1 修正说明**
>
> 原方案（15字门槛 + 60秒停留 + WEAK判定）存在三处根本性错误，已全部废弃：
> 1. **15字门槛**：用"量"衡量"质"。"程序员脱发"四字的信息密度远超凑字应付的废话。
> 2. **60秒停留限制**：与"乱写期越快越好"的设计硬冲突，一个规则否定另一个规则。
> 3. **WEAK判定**：用户脑子里已有 Inner Critic 在说"你写得烂"，系统再盖一个"确实烂，改"的戳，两声叠加，彻底摧毁下次行动的意愿。这不是破冰，是加冰。

### 架构总览（修正后）

```
用户点击【做完了，下一步】
        │
        ▼
   第一层：最低门槛（字数 >= 5，无停留限制）
        │ 通过
        ▼
   第二层：AI 摘要归档（不审判，只记录）
        │
        ▼
   第三层：破冰战报
```

---

### 4.1 第一层：最低门槛（前端）

**唯一规则：字数 >= 5，无停留时间限制。**

- 5字门槛只拦截真正的**空提交**（什么都没写就点下一步）。
- "程序员脱发"四个字就是有效产出，不需要凑到15字。
- 速度快的用户不应该被惩罚，快速完成本身就是破冰成功的信号。

```javascript
const canProceed = userInput.trim().length >= 5;

<button disabled={!canProceed} className={canProceed ? 'active' : 'locked'}>
  {canProceed ? '提交产出 →' : '🔒 请先写点什么'}
</button>
```

---

### 4.2 第二层：AI 摘要归档（不审判，只记录）

**核心原则：AI 在这一层的角色是"书记员"，不是"评审官"。**

用户的原始产出，无论多乱多糙，AI 只做一件事：**压缩成一句话摘要，用于战报展示。** 没有 PASS / WEAK / EMPTY 的判定，没有"你写得不够好，改"的反馈，只有冷静的记录。

**新增后端接口：`POST /api/summarize`**

```python
class SummarizeRequest(BaseModel):
    step_title: str       # 步骤标题
    user_content: str     # 用户原始产出（可以很乱）

class SummarizeResponse(BaseModel):
    summary: str          # 一句话摘要，用于战报

SUMMARIZE_PROMPT = """
你是破冰协议的归档引擎。

用户刚完成步骤「{step_title}」，提交了以下内容：
{user_content}

请将其压缩成一句话（不超过20字），用于破冰战报的归档展示。
不要评价好坏，不要给建议，只提炼核心信息。
如果内容很乱，就从中找出最关键的那个词或那件事。

只返回那一句话，不要任何其他内容。
"""

@app.post("/api/summarize", response_model=SummarizeResponse)
async def summarize(req: SummarizeRequest):
    if client is None:
        # 无 API Key 时降级：截取前20字作为摘要
        return SummarizeResponse(summary=req.user_content.strip()[:20])

    prompt = SUMMARIZE_PROMPT.format(
        step_title=req.step_title,
        user_content=req.user_content[:1000]
    )
    try:
        response = client.chat.completions.create(
            model=MODEL,
            messages=[{"role": "user", "content": prompt}],
            max_tokens=50,
            temperature=0.2,
        )
        summary = (response.choices[0].message.content or "").strip()
        return SummarizeResponse(summary=summary)
    except Exception:
        return SummarizeResponse(summary=req.user_content.strip()[:20])
```

**举例：**

| 用户原始输入 | AI 归档摘要 |
|------------|------------|
| "呃，程序员脱发，就这个吧，随便写写" | `程序员脱发选题` |
| "想写三个标题，第一个...算了第二个...嗯这个还行" | `3个标题草稿` |
| "开头说自己秃了，然后讲三个方法，结尾叫人收藏" | `开头+3方法+CTA结构` |

### 4.4 Done 页下游：AI 驱动的改进循环

> **核心原则**：不给用户选择，AI 决定改什么，用户只管确认。协议是一把刀，但不是一堵墙。

#### 4.4.1 流程设计

```
Done 页面展示破冰战报
        │
        ▼
用户点击【继续改进】
        │
        ▼
AI 分析所有步骤产出，识别最薄弱的一个点
        │
        ▼
[Protocol]: "下一步：[具体改进指令]。确认？"
        │
        ▼
用户点击确认 → 回到 Roadmap，高亮要改的那一步
        │
        ▼
进入步骤编辑页，用户在已有产出基础上修改
        │
        ▼
修改完成 → 回到 Done，更新破冰战报（显示第 N 轮改进）
```

#### 4.4.2 为什么回到 Roadmap，不是直接进步骤页

1. **上下文锚点**：Done 页给了完成感，直接跳步骤页会丢失"我在做什么"的全局上下文。
2. **轮次可视化**：第一轮是完整路线图，第二轮高亮一格，第三轮高亮另一格。用户能直观看到改进进展，而不是在步骤页里原地打转。
3. **与核心流程复用**：改进循环复用"拆解 → 执行 → 成型 → 改进"的步骤机制，不引入新概念。

#### 4.4.3 轮次警告机制（软性强制信号）

**不要硬截断轮次。** 硬截断会在最有价值的时刻把门关上（"轮次已达上限，协议终止"）。真正的问题不是"改了几轮"，而是"有没有在进步"。

| 轮次 | 系统行为 | 文案 |
|------|---------|------|
| 第 1-2 轮 | 正常进入改进循环 | 无额外提示 |
| 第 3 轮 | 进入前插入警告（可忽略） | `[Protocol]: 这是第 3 轮改进。协议建议你完成这一轮后发布或提交，而不是继续修改。你的完美主义正在这里等着你——先把它发出去。` |
| 第 4 轮及以后 | 每轮进入前插入强警告（仍可忽略） | `[Protocol 警告]: 你已经进行了 {N} 轮改进。继续修改的边际收益趋近于零。发布一个 80 分的产出，比打磨一个永远发不出去的 100 分更有价值。这是最后一轮建议。` |

用户可以选择忽略警告继续改进，但系统已经明确表态。

#### 4.4.4 AI 识别改进点的 Prompt 策略

AI 从所有步骤产出中识别**一个**最值得改进的点，遵循以下优先级：

1. **有明显缺口的产出**：某步骤产出明显比其他步骤薄（字数少、逻辑断、缺少关键元素）。
2. **影响整体连贯性的环节**：前后步骤衔接断裂，修改这一处能让整体质量跳升。
3. **用户投入最少的步骤**：耗时最短、字数最少的步骤，往往是最容易快速提升的。

**约束**：
- 每轮只改一个点。"下一轮只改一个东西，不开新战线。"
- 改进指令必须是具体的、可执行的（"把标题改成更口语化"，不是"优化标题"）。

#### 4.4.5 用户拒绝改进时的退出路径

如果用户在 Done 页不点"继续改进"，而是点击"再来一次"或关闭页面，行为不变：

- **再来一次**：重置所有状态，回到 Landing 页。
- **复制/下载**：导出当前产出，协议结束。

改进循环是可选的增值路径，不是必须走完的流程。

## 五、语音输入（待实现）

### 5.1 核心价值

语音输入不是"方便"，而是**破除完美主义键盘输入时过度自我审查的卸压阀**。语速快于脑速，逼迫大脑关闭评判功能。

### 5.2 推荐实现方案

**技术选型：**
- 转录引擎：**OpenAI Whisper**（响应时间必须 <= 1 秒）
- 交互方式：按住说话（Push-to-Talk）或一键触发60秒意识流捕捉

**交互流程：**
```
用户点击 🎙️ → 全屏录音脉冲视觉反馈
   → Whisper 实时转录
   → LLM 语义提炼（去除口头禅、语无伦次）
   → [破冰协议] 回复："收到。基于你的输入，我已提炼出：[核心主题]。是否立即开始拆解？"
```

**按钮文案：** `🎙️ 意识流捕捉`（不要用"语音输入"）

## 六、上下文贯通（Bug 修复）

### 6.1 问题定位

AI 在第二步及后续步骤中表现得"失忆"，不知道用户在第一步确定的任务/选题。

**根本原因：前端 Bug。**
后端 `ChatRequest` 已经包含 `task`、`steps`、`current_step` 和 `outputs` 字段，但前端在进入新步骤时，**没有将上一步的数据作为 Payload 传给后端**。

### 6.2 修复方向

前端在每次发送请求时，必须携带完整的会话状态：

```javascript
const payload = {
  message: userInput,
  history: conversationHistory,
  phase: "step",
  task: sessionState.task,                  // ← 必须传！
  steps: sessionState.steps,                // ← 必须传！
  current_step: sessionState.currentStep,   // ← 必须传！
  outputs: sessionState.outputs             // ← 必须传！
};
```

### 6.3 AI 主动提议（Proactive Context）

修复 Bug 后，当用户进入第 N 步时，[破冰协议] 不应该只是复读步骤说明，而应该主动结合上下文：

> *"基于你在第一步确定的选题【程序员防脱发指南】，我知道你现在需要写 3 个吸引人的标题。需要我直接生成几个草稿供你挑选吗？"*
