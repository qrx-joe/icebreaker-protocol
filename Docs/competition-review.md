## 二、原报告中的错误（已纠正）

### ❌ 删除："16分钟"文案建议

原报告三次使用"16分钟内产出一个可以改的雏形"作为文案建议。这个数字来源于破冰战报的虚构示例（4:32 + 3:15 + 8:47 = 16:34），不是基于实际步骤时长计算的结果。

实际情况：每步上限 15 分钟，3步 = 最多 45 分钟，4步 = 最多 60 分钟。用虚构数据做价值主张不诚实，已从所有建议中删除。

**正确做法**：如果要在文案中使用时间数字，应基于实际步骤配置计算。例如 content 类（4步 × 平均 7.5 分钟 = 约 30 分钟），可以说"30分钟内产出一份可改的初稿"。

### ❌ 删除："花了一整天没改代码"结论

这是时效性判断，写入文档后变成了对项目管理能力的永久性负面评价。代码已实现报告中列出的大部分功能，这句话如果被评委看到反而暴露混乱。已删除。

## 三、当前代码中实际存在的缺陷

以下是原报告未覆盖的、当前代码中真正需要修复的问题：

### 🔴 缺陷 1：第一层验收 5 字门槛未生效

**位置**：前端提交逻辑。
**问题**：当前代码使用 `!output` 检查空值，而不是 `output.length < 5`。这意味着用户输入 1 个字符就能通过验收，5 字最低门槛形同虚设。

**修复**：
```javascript
// 错误：
if (!output) { /* 阻止提交 */ }

// 正确：
if (!output || output.trim().length < 5) { /* 阻止提交 */ }
```

### 🔴 缺陷 2：改进循环跳过 Roadmap 页面 + 前端沉浸感断裂

**位置**：改进流程跳转逻辑（后端 + 前端）。

**后端问题**：用户在 Done 页面点击"继续改进"后，AI 分析并指定改进步骤，但直接跳到了步骤编辑页（`screen: "step"`），跳过了 Roadmap 页面。

**前端问题**：当前 `startImprovement()` 的轮次警告使用浏览器原生 `confirm()` 弹窗，这会**打破协议 UI 的沉浸感**。改进循环应在协议界面内完成——在 Roadmap 页面内联展示改进指令和警告，而不是跳出一个丑陋的系统弹窗。

**应有行为**：按产品设计决策文档约定：
1. 后端返回 `screen: "roadmap"`，高亮 AI 指定的改进步骤。
2. 前端在 Roadmap 页面内展示 `[Protocol]` 的改进指令（含轮次警告），用户在页面内确认后进入对应步骤。
3. 整个流程不使用 `confirm()` / `alert()` 等原生弹窗。

**修复**：
- 后端：改进流程的 `screen` 返回值改为 `"roadmap"`，通过 `current_step` 指示高亮步骤。
- 前端：将 `confirm()` 替换为 Roadmap 页面内的协议指令卡片 + 确认按钮。

### 🟡 缺陷 3：SKILL.md 时长描述与代码不一致

**位置**：`SKILL.md` 第 70 行。
**问题**：SKILL.md 写的是"每步可在 **10-30 分钟**内完成"，但代码中 `Step` 模型已改为 `minutes: int = Field(ge=1, le=15)`。文档与代码不同步。

**修复**：
```markdown
# SKILL.md 第 70 行
# 修改前：
2. **每步可在 10-30 分钟内完成**

# 修改后：
2. **每步可在 1-15 分钟内完成**
```

### ✅ 已解决：改进轮次上限（原缺陷 4）

**原判断**：报告称"用户可以无限点击继续改进，改进轮次无上限"。
**实际情况**：代码已实现完整的轮次警告机制（`startImprovement()` 第 1596-1607 行）：
- 第 3 轮：软性警告。
- 第 4 轮及以后：强警告。
- 使用 `confirm()` 让用户确认是否继续（注：`confirm()` 的沉浸感问题归入缺陷 2 一并处理）。
- 用户可选择停止，轮次回退。

此缺陷不存在，报告误判，已标记为 ✅。
