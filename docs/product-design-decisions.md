# 破冰协议 · 产品设计决策文档

> 当前状态：v2.3.0-dev | 更新日期：2026-06-18

本文档记录当前产品形态、已实现决策和下一步优先级。旧版本中的“待实现”内容已经按当前代码状态重新整理，避免文档继续拿过期假设指挥开发。

---

## 一、产品定位

破冰协议服务的是“完美主义导致的任务启动瘫痪”。用户不是没有计划，也不是不知道重要，而是因为太想做对，所以不敢留下第一个粗糙版本。

核心承诺：

> 不改变你的标准，只先制造一个能被标准加工的对象。

产品不做：

- 不做长期任务管理。
- 不做泛用待办列表。
- 不做情绪陪聊。
- 不鼓励无限优化。

产品只做：

- 把任务拆成可执行步骤。
- 带用户逐步产出雏形。
- 卡住时直接给可用内容。
- 完成后只改一处。
- 用质量评价器判断是否可发布、投递或展示。

## 二、已实现的核心流程

### 2.1 启动契约

首页输入任务后进入契约页，明确：

- 目标是“可以改的雏形”，不是完美成品。
- 每一步都要有明确产出。
- 每一步都有时间限制。
- 唯一不允许的是空白。

### 2.2 路线图拆解

后端优先用 AI 拆解任务；没有 API Key 时使用规则引擎 fallback。

拆解规则：

- 默认 3-6 步。
- 每步必须有可见产出。
- 默认单步 1-15 分钟。
- 复杂任务增加步骤数量，不延长单步时间。

### 2.3 步骤执行

步骤页包含：

- 当前步骤标题和产出要求。
- 三阶段倒计时：乱写期、修整期、紧急状态。
- 主输入区。
- 附件入口。
- 语音输入。
- `[Protocol]` 侧边抽屉。
- 停滞自动介入。

### 2.4 摘要归档与破冰战报

每步完成后调用 `/api/summarize`，将用户原始产出压缩成一句战报摘要。没有 API Key 时截取原始文本作为 fallback。

归档原则：

- 不评价好坏。
- 不给建议。
- 只记录“这一步留下了什么”。

### 2.5 改进循环

Done 页点击“只改一处”后：

1. AI 或规则逻辑选择一个最值得改的步骤。
2. 回到 Roadmap。
3. 高亮目标步骤。
4. 在页面内展示改进指令和轮次警告。
5. 用户确认后进入对应步骤。

轮次策略：

| 轮次 | 行为 |
|---|---|
| 第 1-2 轮 | 正常改进 |
| 第 3 轮 | 温和提醒：完成本轮后建议发布或提交 |
| 第 4 轮及以后 | 强警告：继续修改的边际收益趋近于零 |

### 2.6 产出质量评价

Done 页提供“评价产出”入口，评价维度：

1. 功能完整性
2. 代码 / 产出质量
3. 可展示性
4. 文档 / 注释
5. 受众匹配度

Web 评价器会生成 Markdown 报告。CLI 版本位于 `scripts/review.py`，报告写入 `reviews/`。

## 三、交互与界面决策

### 3.1 `[Protocol]` 命名

继续使用 `[Protocol]`，不使用“AI 助手”。

原因：

- 用户可以对“助手”卖惨，但很难和“协议”讨价还价。
- 去人格化能减少情绪拉扯。
- 对话重点从“安慰我”转向“告诉我下一步做什么”。

### 3.2 右侧抽屉

已采用右侧 Side Drawer，而不是居中弹窗。

原因：

- 不遮挡用户当前输入区。
- 允许用户同时看见步骤要求和协议回复。
- 更符合伴随式工作流。

### 3.3 页面内确认

改进循环使用页面内 Roadmap 确认，不再使用浏览器原生 `confirm()`。

原因：

- 原生弹窗破坏沉浸感。
- 页面内指令可以保留上下文、轮次、目标步骤。
- 这符合“协议接管工作流”的产品气质。

## 四、设置系统

当前支持三类设置：

| 设置 | 选项 | 影响 |
|---|---|---|
| 协议强度 | 温和 / 标准 / 严厉 | 改变 `[Protocol]` 的语气和干预力度 |
| 时间偏好 | 紧凑 / 标准 / 宽松 | 改变单步时间范围 |
| 产出模式 | 草稿 / 可交付 / 作品集 | 改变步骤数量和精细度 |

设置存入 localStorage，并带入后端请求。

## 五、附件与语音

### 5.1 附件解析

支持：

- PDF
- DOCX
- XLSX
- PPTX

附件文本会被截断后带入任务拆解和步骤帮助，避免用户上传材料后 AI “失忆”。

### 5.2 语音输入

当前为 Web Speech API 基础版，入口包括：

- 首页任务输入
- 步骤工作区
- `[Protocol]` 侧边抽屉

待优化方向：

- 接入 Whisper 或其他服务端转录。
- 提供“意识流捕捉”模式。
- 对口语输入做结构化提炼。

## 六、质量与架构观察

当前功能已经形成闭环，但代码层面需要警惕两个风险：

1. **前端模块迁移痕迹较重**：部分模块存在疑似机械改名或拼接造成的异常 import / 状态引用，需要单独做一次构建与静态检查。
2. **本地 FastAPI 与 Vercel serverless 逻辑重复**：`server.py` 与 `demo/api/_common.py` 有相似拆解、回复、摘要逻辑。短期可接受，但继续扩展会产生冗余和行为不一致。

建议下一轮先做“可运行性体检”，再做功能扩展。

|---|---|---|
| P0 | 跑通前端构建并修复模块导入问题 | 当前最可能影响 demo 可用性 |

| P1 | 合并本地后端与 serverless 的共享规则 | 降低重复逻辑导致的不一致 |

| P2 | 升级语音输入为服务端转录 | Web Speech API 兼容性和准确率有限 |
| P2 | 产出评价历史可视化 | 帮用户看到质量趋势，而不是只看单次分数 |

## 八、核心原则

1. 任务复杂性 → 增加步骤数量，不增加单步时长。
2. 空白是唯一失败；粗糙不是失败。
3. 协议不评价用户，只约束动作。
4. AI 回复必须能被直接使用。
5. 改进每轮只改一处，不开新战场。
