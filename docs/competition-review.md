## 二、当前实际风险

### P0：前端模块迁移后存在导入 / 状态引用异常

验证命令：

```bash
cd demo
npm.cmd run build
```

当前结果：构建失败。Vite 在 `virtual:app-core` 报错：

```text
Unexpected token `.`
state.sessionLog: state.sessionLog.map(...)
```

这说明前端模块迁移后存在非法对象键或错误状态引用。这个问题不是文案层面的小瑕疵，而是会直接导致生产构建失败。

建议先排查以下模式：

```bash
rg -n "state\.[A-Za-z0-9_]+\s*:" demo/src
```

把对象字面量里的 `state.xxx:` 修正为合法键名，例如 `sessionLog:`、`steps:`、`stepOutputs:`。随后继续跑构建，直到所有语法错误清空。

### P0：本地后端与 Vercel serverless 逻辑重复

`server.py` 与 `demo/api/_common.py` 都维护了任务拆解、回复、摘要等逻辑。短期为了部署可用可以接受，但继续扩展会带来两个后果：

- 本地 demo 和线上 demo 行为不一致。
- 同一个规则要改两遍，容易遗漏。

建议：把可复用规则沉淀为共享模块，或者明确规定 serverless 只做轻量 fallback，不追求与本地后端完全等价。

### P1：版本号来源不统一

当前 `pyproject.toml` 仍为 `2.0.0`，`SKILL.md` 和文档使用 `2.2.0-dev`。这会让用户不知道哪个版本才是准的。

建议：如果 v2.2 只是开发态，保留 `2.2.0-dev`；如果准备发布，统一更新 `pyproject.toml`、`SKILL.md`、`CHANGELOG.md`。

### P1：评价系统需要更清楚地区分“协议内评价”和“对外发布评价”

破冰协议原本强调“不评价初稿”，但新增产出质量评价器会带来认知冲突：用户可能以为每步都要被打分，从而重新激活完美主义。

建议：文案上明确评价器只在完成后使用，且用于“决定是否发布/投递”，不是审判每一步。

## 四、犀利结论

当前项目最危险的不是功能不够，而是已经进入“功能越补越多，基础可运行性反而没人盯”的阶段。对一个反完美主义工具来说，这很讽刺：你不能一边教用户先交付，一边让自己的 demo 卡在构建错误里。

下一步别再加功能。先跑通构建和完整用户路径。
