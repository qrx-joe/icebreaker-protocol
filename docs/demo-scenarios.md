# 破冰协议 — 现场演示场景与脚本

> 评委/观众坐在下面看演示，最怕三件事：听不懂、看不到产出、感觉跟自己无关。
> 所有场景均满足：**普世痛点 × 5-8 分钟可跑完 × 产出可视化**。

---

## 场景选择标准

| 维度 | 要求 | 原因 |
|------|------|------|
| 观众代入 | 普世痛点，不是小众需求 | 观众必须觉得"我也遇到过" |
| 时间可控 | 5-8 分钟跑完全流程（含 1 轮改进循环） | 路演时间有限，不能卡在执行阶段 |
| 产出可视化 | 屏幕上能展示一个具体"成品" | 看不到产出的演示 = 没有说服力 |
| 现场共振 | 与当下情境有关联 | 观众"在场感"越强，记忆越深 |

### 不适合现场演示的场景

| 场景 | 问题 |
|------|------|
| Python 爬虫 | 5 分钟跑不完，观众看不到代码运行 |
| 个人网站 | 同上，且需要浏览器切换 |
| 简历 | 太个人化，敏感信息没法上屏 |
| 小红书脚本 | 可演示但 toB 评委可能觉得"轻浮" |
| 社交破冰（发真实消息） | 对方不回就尴尬，风险高 |

## 🥇 场景一：路演结束后发一条朋友圈（推荐首选）

### 为什么是最佳选择

观众**正在听你路演**，你演示"路演后发朋友圈"——场景与现场强绑定，观众会下意识思考"我也得发一条"。产出是一条可以直接复制发出的朋友圈文案，**5 分钟从零到可发布**。

### 5 分钟逐秒脚本

| 时间 | 操作 | 台词/旁白 | 设计意图 |
|------|------|-----------|----------|
| 0:00-0:15 | 停在首页 | "路演结束了，我想发一条朋友圈记录今天这件事——但怎么写才不油腻、不自嗨？这种事我通常会想半小时然后放弃。" | 问题引入，代入感 |
| 0:15-0:25 | 输入任务：`路演结束想发一条朋友圈，但怕写得又油腻又自嗨`，回车 | "交给破冰协议。" | 行动 |
| 0:25-0:40 | 展示契约页，点「同意，开始」 | "先签契约——目标不是写出一条完美朋友圈，而是写出一条**可以改的朋友圈**。把标准从'写好'降到'写出东西'。" | 核心理念传达 |
| 0:40-1:00 | 展示路线图（3-5 步） | "拆成 5 步：定基调、写 3 个开头、选 1 个扩写、配图思路、终稿。每步都有明确产出。" | 拆解能力展示 |
| 1:00-1:30 | 第 1 步：定基调 | "第一步——你这条朋友圈想给谁看？想传递什么感觉？随手写，不用想措辞。" 输入："想给同行看，传递一种'做完了松口气、但还有点小骄傲'的感觉" | 乱写期——降低门槛 |
| 1:30-2:00 | 第 2 步：写 3 个开头 | 输入三个开头：①"今天终于路演完了" ②"搞了一周，5 分钟讲完了" ③"比想象中顺利——但也比想象中紧张" | 强制产出 |
| 2:00-2:30 | 第 3 步：选 1 个扩写 | 选第 3 个扩写，补完中间段落和结尾。故意写得一般："今天路演比想象中顺利。虽然准备了一周很紧张，但讲完那一刻真的松了口气。感谢队友，继续加油。" | 为改进循环埋伏笔 |
| 2:30-3:00 | 跳过配图步骤（快速过） | "配图思路先过——路演现场照片 + 一张白板草图。" | 控制时间 |
| 3:00-3:20 | 终稿提交，进入 Done 页 | "初稿出来了——能看，但说实话有点平。" | 过渡到改进循环 |
| 3:20-4:00 | 点击「继续改进」→ AI 指出最薄弱点 | **AI 指出**："开头'比想象中顺利'信息量为零，读者不知道你在做什么。改成更具体的一句。" 用户确认。 | **核心卖点**：协议有牙齿，不安慰只给操作 |
| 4:00-4:30 | 回到路线图，高亮"写开头"步骤，修改 | 改成："为一个完美主义者的启动协议做了路演——对，专门治那种'想太多做太少'的病" | 改进循环实际效果 |
| 4:30-5:00 | 回到 Done 页，展示破冰战报 | "第 1 轮改进完成。5 分钟前我还一个字没写，现在有一条可以直接发的朋友圈。" | 收束，首尾呼应 |

### 亮点功能埋点

| 亮点 | 在哪一步展示 | 怎么操作 |
|------|-------------|----------|
| 附件上下文穿透 | 第 1 步前 | 上传一张路演海报 PDF → AI 摘要后带入拆解 |
| 三阶段倒计时 | 执行阶段 | 指出"乱写期 → 修整期 → 紧急状态"的压力梯度 |
| 60 秒停滞自动介入 | 第 3 步时 | 故意停 60 秒不输入 → 帮助面板自动弹出 |
| 改进循环"只改一处" | 改进循环 | AI 指出只改开头，不改其他——防止无限优化 |
| 轮次警告 | （如时间允许第 2 轮改进） | 第 3 轮温和提醒，第 4 轮强警告 |

### 应急方案

| 状况 | 处理 |
|------|------|
| AI 拆解步骤数不是 5 步 | 没关系，强调"3-6 步都合规，协议有步骤数约束" |
| LLM 响应慢/超时 | 切换到规则引擎 fallback，口头说明"没 Key 也能跑" |
| 60 秒等不了 | 提前说"这里有个停滞检测功能，正常情况 60 秒会自动弹出帮助"然后手动打开侧边抽屉 |

## 🥈 场景二：观众出题——"明天要交的述职 PPT 大纲"

### 为什么效果好

让观众**当场出题**，破除"提前练过"的怀疑。同时，"述职/汇报"是职场最大公约数痛点，几乎每个人都能代入。

### 互动流程

1. **开场抛钩子**："在座有多少人，这周或者下周，有一份述职/复盘/项目汇报要交？"
2. **让观众举手说出自己的任务**，选一个最有代表性的
3. **当场输入，当场拆解，当场执行**

### 预设兜底（如果没人举手）

输入："周五要交一份季度述职 PPT 大纲，一直拖着没动笔"

**拆解预期**：
1. 定核心结论 → 产出：一句话说清"这季度我干了什么、值多少钱"
2. 列 3 个成果 → 产出：每条成果 + 量化数据
3. 补风险和下季度计划 → 产出：PPT 的"问题-对策"页
4. 排版成大纲 → 产出：逐页 PPT 大纲（标题 + 3 个要点）
5. 检查逻辑流 → 产出：可交付的大纲终稿

**改进循环演示点**：AI 指出"成果都是'做了什么'，没有'值多少钱'，加一个业务影响数据"→ 只改这一处

### 亮点功能埋点

| 亮点 | 怎么展示 |
|------|---------|
| 观众互动 = 不可预测 | 现场出题本身就是最大亮点 |
| 规则引擎 fallback | 如果 LLM 慢，当场展示"没 Key 也能拆解" |
| 停滞自动介入 | 故意停 60 秒 |
| 改进循环"只改一处" | AI 精准指出"缺量化数据" |

### 应急方案

| 状况 | 处理 |
|------|------|
| 观众出的题太抽象（"我想变得更好"） | 当场演示协议的**收敛能力**："你有一整天还是只有 2 小时？""想学新东西还是产出成果？" → 给 3 个候选 |
| 观众出的题太技术化 | 换回兜底场景，说"这个更适合技术场景深入演示，我们用一个更普适的例子" |
| 没人举手 | 自然过渡到兜底场景，不要尴尬等待超过 5 秒 |

## 🥉 场景三：写一份 GitHub README（技术评委向）

### 为什么适合技术评委

如果评委里有程序员或产品经理，这个场景**专业感拉满**，而且 README 本身就是"完美主义重灾区"——总想写得完美导致一直拖着不写。

### 演示脚本

- **输入**："我有一个副业项目想开源，README 一直写不出来"
- **拆解预期**：
  1. 一句话定位 → 产出：项目是什么、解决什么痛点
  2. 痛点描述 → 产出：用户在什么场景下会需要这个项目
  3. 核心功能 3 条 → 产出：Feature List
  4. 快速开始 → 产出：3 行安装命令
  5. 截图/占位符 → 产出：完整 README 结构

### 改进循环演示点

AI 指出"一句话定位太技术化了，非本领域的人看不懂"→ 改成用户视角描述

### Meta 加分项

如果破冰协议自己的 README 确实是用协议写的，**直接说**："这个项目自己的 README 就是用破冰协议写的——先出一版能看的，再改了两轮。" 自举（bootstrapping）永远是最好卖的故事。

## 场景四（备选）：写一封拒绝合作的邮件

### 适用场景

面试/职场主题的路演，观众以职场人为主。

### 演示脚本

- **输入**："我要回一封拒绝合作的邮件，怕得罪人一直没动笔"
- **拆解预期**：
  1. 定调性 → 产出：专业/温和/留口子
  2. 三段式结构 → 产出：感谢/拒绝理由/留门
  3. 写完 → 产出：完整邮件初稿
  4. 软化措辞 → 产出：可发送的终稿

### 为什么对完美主义者精准

不敢写 → 怕措辞错 → 反复打草稿 → 最后拖过期。这是完美主义拖延的**经典模式**，协议的价值一目了然。

## 演示策略：一个被忽略的杀手锏

你只想着"演示一个完整流程"，但评委更想看的是 **"AI 在过程中表现出多少判断力"**。

### 建议：故意做一个坏决定

1. 在执行阶段，**故意写一个超烂的步骤产出**
   - 朋友圈开头写"今天好开心"（零信息量）
   - 述职成果写"做了很多事"（零量化）
   - README 定位写"这是一个工具"（零价值）
2. 进入改进循环时，**看 AI 能不能精准指出问题**
   - "这个开头零信息量" ✓
   - "成果缺量化数据" ✓
   - "定位没有说清解决什么痛点" ✓
3. **这个"AI 当场打脸用户"的瞬间**，比顺利跑完 10 个流程都震撼

### 为什么有效

完美主义者最怕"AI 只会鼓励"。你要让评委看见**你的协议有牙齿**——不安慰，不鸡汤，只给下一步操作。这才是协议的核心差异点。

## 演示时间分配建议

| 环节 | 时长 | 内容 |
|------|------|------|
| 问题引入 | 30 秒 | 完美主义者的启动困境 |
| 输入 + 契约 | 45 秒 | 核心理念："做出可以改的雏形" |
| 任务拆解 | 30 秒 | 路线图展示 |
| 执行（2-3 步） | 2 分钟 | 快速执行，展示乱写期/修整期 |
| 改进循环 | 1.5 分钟 | **重点**：AI 指出薄弱点 + 只改一处 |
| 收束 | 30 秒 | 破冰战报 + 金句收尾 |
| **合计** | **约 5 分钟** | |

> 如果有 8 分钟：在执行阶段多停留，展示停滞自动介入（60 秒等待）、附件上传、三阶段倒计时。
